# 3DTool — Procedural Room Preset Library

**Implementation specification for an AI coding agent**  
**Purpose:** Expand the existing open-source Next.js + Three.js application with a modular, editable, high-quality catalog of **room architecture, furniture, fixtures, appliances, and decorations created entirely from procedural Three.js code**.  
**Status:** Agent-ready implementation plan, not a claim that these presets are already implemented.  
**Working repository:** `3dtool`  
**Primary product:** Section 1 / Shape Studio. Section 2 / Future Lab stays a placeholder.

---

## 0. Instructions to the implementation agent — read first

You are working **inside an existing codebase**. Before making changes:

1. Read the repository's `AGENTS.md`, `README.md`, `package.json`, existing tests, and relevant `src/core`, `src/components`, `src/state`, and `src/ai` modules.
2. If `AI_AGENT_3DTOOL_SPEC.md` is present, read it. **This document extends its object-preset scope; do not replace the previously specified two-section app, AI-planner architecture, or deployment constraints.**
3. Inspect what the app already supports, including current `ThreeSceneMaster`, scene schemas, scene command validator, Zustand store, editor controls, and working presets. Adapt to current names/interfaces; **do not rewrite the application from scratch**.
4. Preserve all working features, persisted projects, existing commands, navigation, fonts, styling, Git history, and Zenith deployment files.
5. Implement the phases below **sequentially**. Start by building dependable procedural primitives and high-quality core room objects. Do **not** create empty classes or menu entries that imply 250 functioning presets when they do not exist.
6. Run type-checks, tests, lint/build, and available end-to-end checks. Report only what was actually tested, with blockers explicitly listed.
7. Leave the `Future Lab`/second section as a placeholder. This task is exclusively for the first studio/editor section.

**What the user wants:** The user can describe a room in natural language, e.g., **“Create a cosy living room with beige walls, an L-shaped grey sofa, a walnut coffee table, a tall bookshelf, a floor lamp, and a plant.”** A local CPU-based Hugging Face LLM converts that request into **validated object commands and parameters**. The trusted Three.js engine creates the objects, places them at coordinates, and lets the user edit the whole object **and its individual components** by interacting with the scene or by giving more instructions.

**Critical rule:** The LLM **never writes or executes raw JavaScript/Three.js code**. Only the trusted procedural factory creates geometry from validated data.

## 1. Product boundaries and technical constraints

- **Framework:** Existing Next.js App Router + TypeScript application.
- **3D rendering:** `three`, `@react-three/fiber`, `@react-three/drei`.
- **Interface:** Material UI; use existing application theme and UX conventions.
- **State/history:** Zustand with serializable scene objects and undo/redo.
- **Runtime LLM:** Existing Hugging Face Transformers.js / Web Worker CPU/WASM integration, if present. Do not add a GPU service or paid API.
- **Geometry:** Construct geometry entirely at runtime using native Three.js primitives, curves, extrusion, lathe, custom buffer meshes, groups, and instancing. **No downloaded GLB furniture assets or hardcoded premade mesh files.** Procedural textures generated by code are optional.
- **Hosting:** Zenith remains one CPU-only Next.js service. Three.js **client-side rendering may use the visitor's GPU through WebGL**; that is distinct from a server GPU requirement.
- **Offline/manual operation:** The preset gallery and editor must work without the LLM or network after the app is loaded. Do not block geometry creation while waiting for model inference.
- **Performance:** Reuse geometry/material instances when safe, dispose replaced resources, and avoid unnecessary continuous React renders on every pointer movement.
- **No misleading realism claims:** Aim for visually convincing **stylized / product-render quality** with realistic proportions and materials. Pure procedural geometry is not guaranteed to be photorealistic or manufacturing-grade.
- **Never use arbitrary `eval`, `new Function`, dynamic code execution, or source code provided by the LLM.**

### Existing stack versus scope of this addition

Do **not** add a separate Express/Python server, database, microservice, or TanStack state library merely to build presets. Keep Zustand for scene state and the current Three.js architecture. A scene tree UI can use MUI X Tree View or React Arborist if useful, but use the already-installed component if available.

## 2. Required outcome

A user can:

1. Open **Shape Studio** and add a preset from a searchable gallery.
2. Ask the LLM to create one or several objects with precise sizes, colours, and relative placement.
3. See the resulting room with credible geometry, lighting, shadows, and materials.
4. Click an object, view a tree of its named parts, and select either the object or a part.
5. Drag/move/rotate/scale an entire object with transform gizmos.
6. Modify **semantic dimensions** (e.g., table width, sofa seat count) through the inspector and regenerate only that object while preserving its identity and relevant edits.
7. Edit specific parts, e.g., “Make only the chair legs matte black” or “Remove the sofa armrests.”
8. Change procedural material settings: colour, roughness, metalness, opacity where appropriate, and predefined material profiles (wood/fabric/metal/glass/ceramic).
9. Duplicate, delete, hide, lock, and rename objects; undo/redo operations.
10. Save and reopen a scene JSON document; optionally export generated objects to GLB using the existing exporter.
11. Receive a clear **unsupported** or **clarification** response when a requested shape cannot yet be made.
12. Continue using manual controls when the LLM is unavailable.

**Do not automatically clear an existing scene on a new prompt** unless the user explicitly requests a reset and confirms a destructive change.

## 3. Architecture: semantic preset → procedural parts → scene graph

Implement three distinct layers, reusing equivalent existing code:

```text
User: natural-language prompt OR preset gallery / inspector
                       |
      +----------------+--------------------+
      |                                     |
Hugging Face text planner             Manual UI commands
(text → strict JSON)                        |
      |                                     |
Zod validation / semantic limits / target resolution
                       |
               Trusted dispatcher
                       |
         Serializable Zustand SceneDocument
                       |
                ThreeSceneMaster
                       |
        Registry of procedural builders
                       |
      THREE.Group + named, selectable parts
                       |
            React Three Fiber Canvas
```

### Three distinct concepts

- **Primitive builder:** Draws an elementary shape, e.g., `makeRoundedBox`, `makeCylinder`, `makeLathedVase`, `makeExtrudedProfile`, `makeLeaf`.
- **Object builder:** Composes primitives into a functional object, e.g., `buildDiningChair`, `buildBookshelf`, `buildSectionalSofa`, `buildWindow`.
- **Preset definition:** A named, parameterised variation of an object builder, e.g., `coffee_table_round`, `coffee_table_oval`, `dining_table_rectangular`. Several presets can share a single tested builder.

Avoid hundreds of copy-pasted components. Many catalog items should be variations driven by a **small family of parametric generators**.

### TypeScript contracts (illustrative; align with repository types)

```ts
export type Vec3 = [number, number, number];

export interface EditablePartDefinition {
  key: string;                   // stable: "seat", "legs", "backrest"
  label: string;
  canRecolor: boolean;
  canHide: boolean;
  materialSlot?: string;
}

export interface PresetDefinition<TParams> {
  id: string;                    // "sofa_l_shaped"
  label: string;
  category: string;
  description: string;
  phase: 1 | 2 | 3;
  defaultParams: TParams;
  paramsSchema: unknown;         // concretely use z.ZodType<TParams>
  materialSlots: string[];
  parts: EditablePartDefinition[];
  build: (params: TParams, materials: Record<string, MaterialSpec>) => THREE.Group;
}

export interface ProceduralPartTag {
  objectId: string;
  partKey: string;               // stable across rebuilds
  materialSlot: string;
}
```

Prefer fully typed schemas and builders in actual code. If you already have `SceneObject.kind`, **keep it working**. You can map preset IDs to existing builder kinds, or introduce an optional `presetId` and migrate existing scene versions safely. Never silently invalidate saved projects.

### Master class behaviour

`ThreeSceneMaster` should:

- Resolve the object/preset type through an explicit registry (not `if` chains spread across pages).
- Build a `THREE.Group` with `userData.objectId` and nested `userData.partKey` tags.
- Apply the transform exactly once, not once in builder and again in React Three Fiber.
- Expose supported presets/parameter schemas/editable part metadata for UI and LLM context.
- Offer deterministic rebuilds of a single object without changing its persistent ID or selection.
- Compute world-space bounds, used for basic room placement and collision detection.
- Dispose unused geometries/materials/textures correctly, taking shared instances into account.

## 4. Coordinate conventions and object rules

- Units = **metres**. Width = X, height = Y, depth = Z. Three.js is **Y-up**.
- Floor ground plane at `y = 0`.
- Default object pivot = **bottom centre**. At position `[0,0,0]`, furniture rests on the floor; hanging/wall-mounted objects use explicit placement rules.
- Persist rotation in radians, consistent with the existing scene schema; inspector may show degrees.
- Store objects as **serializable specifications**, not live `THREE.Mesh` instances in Zustand.
- Preserve object identity, part overrides, transform, name, visibility, and lock status on parameter rebuild.
- Stable semantic part keys: `top`, `legs`, `left_armrest`, `right_armrest`, `backrest`, `seat_cushion_1`, `frame`, `glass`, `handle`, etc.
- A part can have a material override and optional visibility override. For Part 1, editable subcomponents need not all have independent physics or transforms; support independent colour/visibility first, then part transforms where well-defined.
- Maintain valid room geometry. A standalone window panel is **not** automatically a hole through a wall. True window/door cutouts require a wall-opening builder or partitioned wall segments; implement those separately and never claim a cutout that is not present.
- Place groups using sensible bounds. Do not rely on LLM-generated exact coordinates for “beside/on top of” requests when the application can compute them.

## 5. The procedural realism standard

Models should look like purpose-built room objects, **not stacks of sharp-edged blocks**. Use the simplest practical technique that noticeably improves quality:

1. **Proportions:** Accurate-ish furniture dimensions in metres; realistic seat heights, tabletop thickness, cabinet depth, and clearances.
2. **Rounded details:** Rounded bevelled tabletops and cushions, smoother cylinder caps, curved profiles for shades, cushions, vases, and fixtures.
3. **Structural details:** Visible sofa cushions and legs, proper chair backrests, cabinet handles, doorframes, window mullions, shelf thickness, and believable joins.
4. **Materials:** Distinct wood, matte/polished metal, fabric, leather-like, glass, plastic, ceramic, and stone profiles. `MeshStandardMaterial` / `MeshPhysicalMaterial` only as appropriate.
5. **Rendering:** Ambient + directional lighting, soft shadows, tone mapping, neutral background, optional grid and ground shadows; keep quality/performance configurable.
6. **No external asset dependency:** No remote furniture meshes or required remote textures. Optional procedural grain/noise from code is acceptable.
7. **Smart repetition:** `InstancedMesh` for slats, tile patterns, books, foliage, repeated screws, etc. Avoid excessively high tessellation.
8. **Preview quality:** Capture screenshots of core presets from multiple angles and visually inspect them.

Treat **realistic** here as *coherent real-world dimensions, recognisable details, convincing materials and presentation*. Do not promise photorealistic fabric, arbitrary organic sculpting, or CAD accuracy.

## 10. LLM / scene command integration

**Existing validated protocol takes precedence.** If the repository already has a `ScenePlan` operation schema (`create`, `set_params`, `set_material`, `set_transform`, `place_relative`, `duplicate`, `delete`), extend that rather than introducing a second incompatible JSON command language.

The new registry must provide compact metadata to the planner:

- Supported preset IDs and natural-language aliases.
- Parameter names, types, defaults, and safe ranges.
- Editable part keys and material slots.
- Whether an object belongs on the floor, on a wall, on a table, or on a ceiling.
- Approximate/known footprint for layout planning.

### Example: create furniture

Illustrative format below. **Conform to the actual project's parser/schema** if its envelope differs.

```json
{
  "version": 1,
  "status": "ok",
  "message": "Creating a sofa and coffee table.",
  "operations": [
    {
      "op": "create",
      "ref": "new:sofa1",
      "kind": "sofa_l_shaped",
      "name": "Grey L-shaped sofa",
      "params": {
        "width": 2.6,
        "depth": 1.65,
        "height": 0.88,
        "chaiseSide": "left"
      },
      "materials": {
        "fabric": { "color": "#888888", "roughness": 0.93, "metalness": 0 },
        "legs": { "color": "#202020", "roughness": 0.48, "metalness": 0.72 }
      }
    },
    {
      "op": "create",
      "ref": "new:table1",
      "kind": "coffee_table_rectangular",
      "name": "Walnut coffee table",
      "params": { "width": 1.1, "depth": 0.6, "height": 0.4 }
    },
    {
      "op": "place_relative",
      "target": "new:table1",
      "anchor": "new:sofa1",
      "relation": "in_front_of",
      "gap": 0.45
    }
  ]
}
```

**Do not copy this example blindly:** `sofa_l_shaped` is **Phase 2**. During Phase 1 it must be rejected with a friendly message or mapped to a supported sofa **only with explicit user agreement**; never silently pretend to create unsupported geometry.

### Example: edit a specific component

User: “Change only the coffee table legs to black.”

```json
{
  "version": 1,
  "status": "ok",
  "message": "Making the selected table's legs black.",
  "operations": [
    {
      "op": "set_material",
      "target": "selected",
      "part": "legs",
      "changes": { "color": "#111111" }
    }
  ]
}
```

### Additional command safety

- Reject extra fields, unknown preset IDs, unknown part keys, out-of-range dimensions and arbitrary nested JSON.
- Enforce existing operation/object/polygon limits and avoid runaway generated instances.
- Bound model output length. Validate the entire plan **before mutation**, then apply commands as an undoable transaction when feasible.
- Resolve target IDs through application state; the LLM never chooses persistent UUIDs.
- If reference targets are ambiguous or absent, ask a question instead of editing a random object.
- Use scene/world bounds for `on_top_of`, `left_of`, `in_front_of` placement; adjust correctly for rotation and grounded pivots.
- “Create 4 chairs around a dining table” should use a deterministic layout helper in app code; the LLM should not have to invent every coordinate.
- Keep clear/reset behind explicit user intent and confirmation.
- If the model fails to load, use manual preset browsing/editor controls rather than misrepresenting hardcoded output as AI.

## 11. UI requirements

### Main Studio layout (reuse current panels)

- **Left:** Searchable **Preset Library** with 18 categories, available presets first, and an **“Available now”** filter. Do not make unimplemented entries clickable as if functional.
- **Center:** Three.js room canvas with grid, orbit, select, translate, rotate, scale, focus, reset view, and optional shadow toggle.
- **Right:** Property inspector with object type, dimensions, position, rotation, scale, material slots, part visibility, and part selection.
- **Scene tree:** Hierarchical object → named parts. Clicking a part focuses/selects it; clicking an object selects the group. Child parts may be simplified if lots of geometry is instanced.
- **Bottom or side:** Chat/prompt panel with AI loading status, validated plan summary, execution error messages, and undo.
- **Navigation:** Two existing app sections remain intact; no change to Future Lab except to preserve its placeholder.

### Interactions

- Add a preset by clicking a card, then place it at scene centre or a preview-supported click location.
- Change dimensions via validated numeric fields; show units (m/cm).
- Direct edits and LLM changes must use the **same command/store pathway**, keeping history consistent.
- Preset gallery shows a generated **small procedural preview** where affordable, or a simple category icon; avoid remote image downloads and heavy concurrent renderers.
- Support keyboard delete, undo/redo, Escape deselection, and accessible controls where available.

### Performance safeguards

- Lazy-load the 3D editor client-side if required by Next.js SSR restrictions.
- Memoize builders and rerender only changed objects.
- Limit geometry segments and shadows; use instancing for large repeats.
- Avoid spinning up a WebGL context for every preset thumbnail.
- Release resources when replacing/removing objects; avoid double-disposal of shared resources.
- Keep Web Worker model separate from rendering and user interactions.

## 13. Tests and acceptance criteria

Use unit tests for builders/validation and browser tests for rendering/interactions. At minimum test:

1. Every registered preset has a unique ID and a valid parameter schema.
2. Every **implemented** preset creates a finite `THREE.Group` without throwing.
3. Each registered component part has stable nonempty `partKey` metadata.
4. Generated geometry has valid bounding dimensions, normals, and sensible floor contact.
5. Zero/negative/non-finite measurements are rejected before geometry creation.
6. Changing table width moves supporting legs appropriately and preserves object ID.
7. Editing only a chair's `legs` material leaves the `seat` material unchanged.
8. Hiding a sofa armrest does not delete the whole sofa; relevant state survives rebuild.
9. Scene save/reload preserves supported kind/preset, parameters, materials, part overrides, transforms and visibility.
10. Existing old `box`, `table`, `chair`, `shelf`, `lamp`, and `sofa` scenes still load.
11. Relative placement respects bounds and metres.
12. Room generator creates a sensible grounded floor with walls at appropriate edges.
13. Gallery exposes only implemented presets as usable, not planned-only entries.
14. Adding/removing many objects does not cause unbounded geometry/material leakage.
15. Model output containing unsupported preset IDs or JavaScript/code is never executed.
16. A model-unavailable state still permits full manual preset creation/editing.
17. Undo/redo works after geometry rebuild and a batch of create/delete operations.
18. Selecting nested parts from the hierarchy or canvas edits the intended part.
19. GLB export, if supported, includes visible procedural geometry and does not require external objects.
20. Production Next.js build succeeds, and single-service Zenith files remain valid.

### Required manual visual inspections

- [ ] Dining table + four chairs: recognisable proportions, adequate leg placement, no intersecting tabletops.
- [ ] Living room: sofa, coffee table, rug, plant pot, lamp and wall art are visible and grounded.
- [ ] Bedroom: bed, headboard, side table and lamp look clearly different from generic cuboids.
- [ ] Room shell: floor/wall alignment sensible; no false wall cutout claims.
- [ ] Material changes: wood, fabric, metal and glass look visibly distinct.
- [ ] Small screen: inspector/chat/editor controls remain usable.

## 14. Contributor guidelines for future presets

To make adding 200+ presets sustainable:

- Implement one focused builder per **object family**, not per minor variation.
- Define a typed parameter schema with minimum/maximums and defaults.
- Declare material slots and semantic part keys.
- Provide a deterministic builder, without side effects or asset downloads.
- Register ID, category, label, supported status, tags and a short description.
- Provide 1–2 example prompts, bounding-box tests and a screenshot where practical.
- Document known geometry limitations; e.g., door panel does not cut a wall.
- Avoid allocating duplicate material/geometry objects needlessly.
- Add regression checks for persistence, selection and part editing.
